# Product behavior and audience

[简体中文](./product.zh-CN.md)

Vista is a general-purpose agent with a browser interface. Users describe a goal, provide relevant paths or attachments, and work with a model that can call tools. The executable contains the Go service, conversation Workers, and embedded Vue interface.

## Audience and design baseline

Vista primarily serves people who can independently use and configure everyday computer or phone software:

| User profile | Typical capabilities |
| --- | --- |
| Proficient everyday use | Manages files and folders, installs software, changes common settings, and searches for solutions. |
| Advanced tool use | Also combines tools, extensions, batch processing, or simple automation and follows instructions to complete unfamiliar configuration. |

Programming, command-line, API, and service-deployment knowledge are not prerequisites.

Use these principles when changing the product:

- Clear defaults and instructions let users with everyday software skills start independently.
- Progressive settings let users configure additional models, skills, and MCP tools by following instructions, without complicating everyday use.
- Explain unfamiliar controls through their purpose, benefits, and costs.
- Automatically updated views have no routine Refresh button. A manual check remains when automatic checks are infrequent and users need an immediate check, such as model catalog updates.
- Describe Vista through tasks and collaboration without assuming it runs on the user's own computer.
- More advanced users retain configuration room. Technical ability and willingness to study configuration are separate; assess desktop and phone use separately.

## Profiles

Choose the current Profile below **Manage sessions** in the sidebar to open the Profile switcher. Select a name to switch, or use its row actions to open in a new tab or rename it. Use **New Profile** at the bottom to add a Profile without leaving the current one. The tab’s address determines its Profile. Existing bookmarks and data stay in the default Profile.

Profiles have separate conversations, model connections, proxy preferences, user skills, MCP configuration and resource libraries. They share the Vista service address and device capacity. Profiles are not a security boundary for tools that access the host filesystem.

## Conversation behavior

- First use connects a model provider in Settings. Built-in connections encapsulate provider setup; a custom connection explicitly selects its API format and authentication. Model availability depends on the connected service and account.
- The first sent message creates a conversation and Worker. Open conversations have resident Workers, subject to admission and health checks. Navigating away or closing the browser leaves work running; closing a conversation stops its Worker and managed work but retains history. Deletion removes its stored conversation data.
- On touch-first devices, Enter inserts a new line; tap Send or use Ctrl/Cmd + Enter with a keyboard to send. On desktop, Enter sends and Shift + Enter inserts a new line.
- The sidebar session menu offers renaming, confirmed closing, and confirmed deletion. Sidebar, conversation-header, and session-manager titles save inline when the editor loses focus.
- Pinned sessions appear first in the sidebar and session manager. The sidebar orders each group by descending creation time, with descending IDs breaking ties; the session manager applies its selected sort within each group.
- The session manager requires confirmation before closing sessions with running tasks or background processes, including batches. Idle sessions close directly from the manager.
- The agent can find and read saved conversations, including closed ones, without reopening them. When asked to tidy idle conversations it proposes closing, which keeps history. Confirm the exact selection in the conversation; Vista skips targets that are no longer idle or have changed. Agent-requested deletion is separate, requires explicit intent and confirmation, and only applies to already closed conversations.
- Main-thread execution is sequential per conversation. Other conversations, child tasks, and tools may run concurrently. Messages sent during execution join at the next decision boundary, before the next model request. Cancellation and failure pause undelivered inputs; a fresh send after execution stops can start new work without automatically resuming paused messages.
- Restart restores Workers for open conversations, records the old execution as interrupted, and automatically continues eligible agent tasks from saved context under normal admission. Canceled, completed, failed or closed tasks, pending questions, and manual compaction do not resume. Completed tool results are reused; unknown outcomes must be checked before retrying. Managed background processes and child tasks are stopped, with no preservation or reattachment guarantee.
- Selecting text in user messages or assistant replies adds numbered quotes above the composer without changing the typed question. Multiple selections, including from different messages in the conversation, accumulate as independently removable and expandable cards in a bounded scroll area. Draft display and sent quote numbers follow the remaining order from 1 after removal, restoration or adding new quotes. Stable internal IDs preserve card identity and source navigation; already-sent messages are not renumbered. Source controls return to the original message when it still exists. Quotes and the question are sent together as separate numbered Markdown blocks with source role, sequence and time where available, so history and model input retain their boundaries. Failed sends preserve the draft, full quote text and numbering; the existing combined input-size limit still applies. The home composer and each conversation save their draft on the Vista service, including text, quotes, and uploaded originals. Normal reads and saves are silent; only failures and version conflicts appear next to the composer. Retry a failed read or write without discarding the current input. Saving from home does not create a conversation. A delayed save cannot replace a newer revision; Vista keeps the current editor text if another tab already saved. Accepted sends clear only the matching revision. Until the server acknowledges a write, the tab temporarily keeps the unacknowledged text, quotes and uploaded references to recover on reload. A newer server revision is not overwritten. Older browser drafts can be imported when the server has no saved revision. Media bytes are stored in the existing resource library.
- Expanded tool text, logs, Markdown, search results and project-instruction lists share bordered result cards with a heading, Copy result and Enlarge result. Search matches are grouped by full file path, with separate line numbers and context rows; partial-result and permission warnings remain visible. Long bodies scroll inside the card without truncating loaded content. The larger dialog reuses the loaded result, keeps Markdown formatting, and restores the inline scroll position when closed; copying Markdown preserves its source. Existing file-diff cards keep their dedicated view, while single-line status summaries remain lightweight. Tool errors and exit status appear below their rendered output with matching width and horizontal edges; an error without output remains visible on its own. These controls add no second default collapse layer and do not change output loading, caching or retry behavior.
- Two or more consecutive searches, directory listings, file reads or webpage reads in the same task form a collapsible lookup summary. It shows representative queries or targets, known search outcomes and failed or interrupted lookups even while closed. A message, other visible activity or a switch between tasks ends the group. Opening it reveals the original steps in order; open an individual step to read its saved output in the same result card. The group adds no extra result read and changes neither conversation history nor tool execution.
- Text, execution details, questions and usage stay with their originating messages. Execution details include child activity in event order; large tool outputs and child reports load on demand. An execution that continues without a new user message shows its live reasoning and tool steps in the same timeline without adding a message. Current action, elapsed time and last activity stay inside the composer status header. Checklists are internal model working context with persistence and restoration, not icons, popovers, chat messages or dedicated detail views; agents do not narrate their maintenance. Users receive useful progress, blockers and final results. Pending inputs sit above the composer card. The sidebar distinguishes foreground execution, background-only activity, unread replies, pending answers, paused queues, unavailable Workers and failures.
- When an internal checklist still records pending or in-progress work, normal completion continues the same execution so the agent can finish authorized independent work or reconcile statuses from existing evidence. Genuine blockers may end execution; cancellation and questions still stop as usual. Repeated attempts to finish without resolving the checklist can keep requesting model turns until you stop the execution. No checklist or already resolved work adds no model request. This is a completion safeguard, not an approval mechanism or independent verification of results.
- Reply footers show TTFT beside TPS: the wait from a model request to its first text or visible reasoning. A reply uses its first measured main-session request, not an average or a child task’s timing; usage details retain each call’s value. Measurements survive refresh. Historical requests and calls without text/reasoning show “—”, not zero. The connection usage view aggregates the same request measurements; neither view uses them to rank models.
- Structured questions can show follow-ups for the selected branch. Only applicable questions appear in navigation and require answers; changing a choice clears dependent answers without clearing unrelated questions. A custom answer selects no predefined branch, so the agent can ask an appropriate follow-up after submission. Choices remain editable until submission, and switching known branches does not call the model. Question drafts are scoped to the pending request in browser session storage; ordinary messages can still replace the questionnaire.
- Pending structured questions use answer mode in the bottom composer rather than another interactive form in history. The header’s Response options remain available. The answer pane has no switch to an ordinary text reply; per-question custom text answers remain available when the question allows them. Existing text drafts, quotes, images and question answers are preserved, and an ordinary message from another client can still replace the pending request. Active typing or input-method composition defers takeover with a waiting notice. Failed submissions keep the form for retry; accepted answers restore ordinary input without waiting for the model to finish, unless a new question is already pending. The current question body scrolls within a bounded card while navigation and submission remain reachable.
- When reading the latest reply after the most recent user message has scrolled out above, Recently sent shows a one-line reference below the title. View sent message opens the full original without moving history; Go to sent message returns to its source. The reference hides while the source is visible, reading earlier history, viewing overlays or showing pending inputs; short viewports use a header icon. This presentation does not add a message or repeat text in model context.
- Viewing an error clears its unread reminder while retaining the session's execution-failed state. Pending questions, paused inputs, and unavailable Workers continue to need attention.
- Temporary model-service failures can retry the same request up to three times without repeating completed tools. Waiting is visible and cancellable, and survives page reloads. Known authentication, quota and protocol errors, and failures after output has started remain terminal. After a failure, Continue execution sends a continuation in the same conversation using the retained history; it preserves unsent drafts. See [request recovery](./architecture.md#model-request-recovery) for eligibility and wait limits.
- A model may finish normally without a final text reply, including after delivering results through tools. Vista completes the usual input and required-task checks and shows that execution ended without text; it does not add an assistant message or treat this as proof that the requested outcome is correct. Request and protocol errors remain failures.
- Select the conversation default in Settings → Model connections. The composer has no model picker. The WebUI follows the configured default for subsequent requests without rewriting earlier model history or switching an admitted execution. The header’s **Response options** icon opens reasoning effort and [processing tier](./providers.md#processing-tiers) where the model can be adjusted, including before the first send. The composer does not duplicate these controls. No confirmation is required, and closing the popover preserves the draft.
- Choose the default model by use in Settings: conversation, image generation, video generation, and classification and scoring. The search lists are grouped by saved connection; media bindings do not require a protocol choice or a model ID. Ask for an output in chat; a tool-capable conversation model can request it without changing the conversation model. Generation shows a card on the originating message, can continue during steering, and saves successful originals as [Session resources](./resources.md). A requested single-task stop is handled through the agent; Stop current execution stops the full execution. A stopped wait is not confirmation that the provider canceled or will not charge.
- Automatic conversation titles are enabled by default and can be disabled at the bottom of Appearance. When enabled, a separate model request generates the first title without tools or an explicit reasoning effort; it may fail independently. When disabled, new conversations display a localized default name followed by their creation time in `YYYYMMDDHHmmss` form, such as “New Session-20261025174143”. The timestamp uses the client’s local time. Existing and manually assigned titles are preserved.

See [architecture](./architecture.md) and [process lifecycle](./process-lifecycle.md) for runtime ownership.

Manage sessions searches and filters the entire saved session list, loading one page of summaries at a time. It defaults to 10 per page, with 20/50/100 available; bulk selection applies to the current page.
Status filters include the total, open, and closed counts; search, filters, and pagination stay visible while the list scrolls.
Click a row’s title or information area to enter the conversation; closed sessions reopen before navigation. Pinning and the row menu remain separate actions; the menu offers renaming, closing, retrying an unavailable Worker, or confirmed deletion.
The list toolbar offers Select and sorting by creation time or recent update, in either direction; newest creation first is the default. Sorting applies to all matching sessions before pagination, with pinned sessions first.
Recent update uses the latest persisted conversation event, including messages, execution records and title changes, or creation time for an empty session; reading, pinning, opening and closing do not change it. Row timestamps show the selected time field.
Select enters bulk selection mode, where clicking a row selects it and the action bar shows operations applicable to the selected sessions.
Changing the search, status filter, sort, page, or page size clears the selection; Done exits selection mode.

About Vista → Advanced settings → Memory and capacity offers Background processes per conversation, default 4, range 1–1024. Saves reach resident Workers; new Workers use the current limit. Lowering it preserves existing jobs and only restricts new starts. Excess starts fail without queuing. This is not a CPU or memory quota. Background jobs optionally specify a total runtime and an advance warning. Omitting both means no deadline; specifying only a timeout disables warnings. A warning never extends the hard deadline. Within authorization, the model can explicitly adjust it or stop the job, but cannot override a user-imposed hard deadline.

## Scheduled tasks

Open **Scheduled tasks** in the sidebar of the Profile you want to use. Enter a name, the message to send, and a one-time, fixed-interval, daily or weekly schedule. Check the time zone and next run before enabling. Leave the model blank to use the Profile's current default when each run starts. An unavailable selected model needs attention rather than switching models.

The Vista service creates a new conversation at each trigger and sends the saved text as an ordinary user message. Creating a task does not start a conversation. Closing the browser does not stop a schedule; Vista must be running to execute. Open the conversation from run history. Execution uses the Profile's ordinary tools and confirmation rules. After the run ends Vista closes the conversation, retains its history and stops its managed work.

Pause stops future triggers, Stop this run stops only the current execution, and Run now does not move the schedule. Only one execution of a task can be active at a time. Vista can start the latest missed trigger within ten minutes; it does not replay a backlog. An expired one-time trigger can still be run manually. Fixed intervals use elapsed time; calendar times use the saved zone and do not run twice when a clock time repeats.

Each active execution has a 30-minute time limit. A question keeps the conversation open and pauses the schedule; answer in the same conversation and resume the plan when ready. An interrupted execution with an unconfirmed result also pauses the schedule and is not started again automatically.

## Context and resources

Completed model turns and tool results survive later messages and Worker restarts. Explicit upstream context-overflow evidence triggers compaction and retry of the failed request. Click the conversation header's **Context** icon to view the retained-context estimate and compaction tradeoffs. The popover stays available during execution; only its **Compact context** action requires an available, idle session. Manual compaction uses the same checkpoint mechanism while idle and does not send or continue automatically. The estimate is neither cumulative usage nor a model-capacity percentage. See [compaction](./context-compaction.md).

Images use shared original files with conversation-owned references. New attachments or explicit resource reads activate visual input for the next supported request; earlier images are not automatically resent. Closing retains ownership; deleting a conversation releases its links, and fully unreferenced files can be cleaned manually. See [resources](./resources.md).

About Vista’s Advanced settings provides memory presets and custom total, per-conversation and active conversation limits. The active conversation limit includes foreground tasks and background activity, counts each conversation once, and excludes idle conversations; it does not limit how many conversations can be open. It shows measured resident usage; reaching the budget refuses new heavy work, and exceeding a Worker limit interrupts that conversation. These are soft guards rather than an OS memory ceiling; external tool processes use additional memory.

Editing and withdrawing sent messages roll back conversation/model history only. Files, shell effects, and remote changes remain. See [message rollback](./message-revert.md).

## Personalization and extensions

- Global instructions are the user's configuration-root `AGENTS.md`, read at execution start. Filesystem tools automatically check their target paths, and shell tools check their working directory for scoped rules. Operations proceed immediately when no new rules need reading; new or changed rules must be read before the model retries or revises the operation. Nearer rules take precedence within their scope, and explicit current requests take precedence over defaults.
- Long-term requirements use the same `AGENTS.md` files whether edited in Settings or maintained in chat. The main agent's `edit_instructions` tool supports `read`, `append`, and exact `replace` (empty replacement deletes a passage). Global scope targets the configuration-root file; project scope requires an explicit absolute directory and targets its `AGENTS.md`. Reads paginate, writes require the current SHA-256, and ambiguous replacements fail without a write. Temporary requests are not persisted. Authoritative-source and synchronization rules still apply; linked/generated files must be maintained through their prescribed process. Project loading and existing `CLAUDE.md`/Copilot compatibility are unchanged.
- The maximum delegation depth defaults to 1 and accepts 0–8. Zero disables child delegation. This is a maximum, not a fixed number of levels the model must create. Required task reports arrive automatically before finalization; waiting parents remain available for user input. Best-effort and detached tasks have different lifetimes.
- System skills are embedded in Vista, visible as read-only entries in settings, and updated with Vista without being extracted to the user directory. The bundled `vista-guide` helps configure and troubleshoot Vista. Users place their own skill folders containing `SKILL.md` in the configuration-root `skills/` directory; the settings list updates automatically. Each execution receives system and user skills' names, descriptions, paths, and sources; full instructions and supporting documents are read on demand. Descriptions follow Agent Skills' limit of 1024 Unicode characters. Clicking a skill name expands its initially collapsed description. User entries show their full paths; system entries omit paths. Skills have no enable/disable state. The skill editor provides a directory tree for existing files: UTF-8 text is editable, raster images can be previewed, and other files show metadata only. Desktop shows the tree beside the file; mobile opens each file from the tree with a Back control. Switching files retains drafts, closing requires confirmation to discard changes, and saving rejects a changed source revision. Embedded system skills remain read-only, and the editor does not create, rename or delete individual files.
- MCP connections supply tools over local stdio or remote Streamable HTTP, with enable/disable controls and connection-scoped credentials. They do not provide MCP resources, prompts, sampling, or elicitation.
- MCP OAuth uses manual callback submission: open or copy the authorization link, complete authorization, and paste the complete callback address into the same Vista dialog. The callback page does not need to load, and no automatic callback listener is started. Attempts expire after five minutes; closing the dialog cancels them. Callback links contain short-lived authorization information and should not be sent in conversations or logs. Codex and Copilot continue to use device-code login.
- MCP and skills settings can import OpenCode v1/v2 configuration through an explicit read, selection, and confirmation. Existing entries are kept. Skill imports copy complete folders, including supporting and binary files; MCP imports save compatible configuration; enabled services connect asynchronously after import. Unsupported entries are shown with reasons. See [import contracts](./architecture.md#providers-and-tools).
- Model web access configures separate search and page-reading services, order, keys, and initial output lengths. Search returns sources and summaries; public page reading uses Jina Reader or DeepSeek; local/internal text pages can be fetched and converted by Vista without third-party submission.
- Network configuration manages shared proxy profiles and independent Global requests/model-connection selections. Clients default to direct and ignore environment proxy variables. See [network configuration](./network.md).

Settings → Storage manages the fixed local directory or encrypted object storage. Changes keep reading/writing at the source while synchronizing in the background, then atomically switch after complete verification. Cancelled, interrupted and retired copies use the same unreferenced-resource cleanup. Conversation databases, settings and process logs do not move. See [resource contracts](./resources.md).

## Configuration editing

Settings and About Vista use JSON Forms for the nine configuration sections below. The agent editor also includes global instructions from `AGENTS.md`. Scalar, choice, object and list fields reuse Vista controls. There is no raw JSON text editor or mode switch. Schema-validated form drafts require an explicit Save changes action; invalid field values block saving. Existing business groups keep their descriptions and figures beside the relevant controls; JSON Forms renders those groups rather than deciding their placement. Search/page-reading service lists show fixed names and only move up/down: they are permutations, not per-row service replacements. Schema and business validation show specific messages and visible invalid borders on the actual fields, not a generic highlighted-fields notice. Personalization shows global instructions, memory and delegation with their figures. Global instructions are edited and saved in a full-screen dialog; the delegation heading opens a secondary depth editor. Group saves submit only their own changed field. Automatic titles keeps its direct toggle at the bottom of Appearance. Preview limits count UTF-8 bytes; 0 means unlimited.

When a settings view receives changed values while a draft is active, the form keeps the draft, including invalid field values, and blocks saving until current values are reloaded. Reloading asks for confirmation before discarding the draft. Service configuration checks the compact `server` section revision; network settings/checks use an opaque private-section revision, and model connection edits use their settings version. These checks do not compare the complete application document. Other settings retain their existing save behavior.

Forms contain the editable fields for each setting type, never the complete `config.json` root or `key.json`. Newly entered credentials use masked, write-only form controls; saved credential values are not returned to the form. Provider selection, model discovery, OAuth and imports retain their existing workflow and typed APIs. Schema renderers replace the ordinary and password/header inputs instead of maintaining parallel handwritten forms, preserving masking, blank-to-reuse and explicit-clear behavior.

The configuration root has three fixed user configuration filenames: the main `config.json`, static-credential `key.json`, and optional global `AGENTS.md`. Both JSON files are private `0600` documents in a private configuration root (`0700` where Unix permissions apply). The main requires integer `version: 2`; its nine raw JSON sections are optional. In a fresh empty root, Server startup or an explicit write may initialize the current files; this is initialization, not conversion of old state. An absent section retains its existing defaults or environment fallback. Explicit `null` and empty values remain distinct from absence through storage and credential splitting; the section's typed validator and API still determine valid values and behavior.

| Section in `config.json` | Purpose | Startup migration input only |
| --- | --- | --- |
| `server` | Saved listening port, separate from the running listener | `server.json` |
| `capacity` | Memory budgets and active conversation limits | `capacity.json` |
| `agent` | Delegation depth and automatic conversation titles | `agent-settings.json` |
| `search` | Search/page-reading services, order and output preview limits | `search.json` |
| `userAgent` | HTTP client identity settings | `user-agent.json` |
| `models` | Model connections and model settings | `models.json` |
| `mcp` | MCP server definitions and connection settings | `mcp.json` |
| `network` | Proxy profiles, global egress selection | None |
| `storage` | Resource backend definitions and credential references; active state is in SQLite | None |

`key.json` requires integer `version: 1`; its `entries` object maps opaque references to `{section, owner, values}` bundles. Managed model and MCP records, proxy profiles, resource backends, or the `search` object, carry `credentialRef` in the main document when they refer to such a bundle. Owners follow stable identities, not display names or array positions; reference/owner spellings are not user-editable identifiers.

| Section | Static fields stored in `key.json` |
| --- | --- |
| `models` | `apiKey`, `accessToken`, `authToken`, `appCode`, `headers` |
| `mcp` | `token`, `clientSecret`, `headers` |
| `search` | `apiKeys`, `jinaApiKey`, `deepseekFetchApiKey` |
| `network` profiles | `username`, `password` |
| `storage` backends | `accessKey`, `secretKey`, `sessionToken`, `masterKey` |

Custom header values are treated conservatively: the entire `headers` object moves, not just headers whose names resemble authorization fields. Public `clientId`, routing and identity settings stay in `config.json`. SDK-managed OAuth accounts, refresh tokens and login directories stay separate; this does not migrate OAuth tokens or redesign authorization.

This is file isolation only, not encryption or a system-keyring/cloud-KMS integration. The key file remains plaintext, and private permissions do not protect it from processes running as the same user. The main file can still reveal internal addresses and project/account identifiers, so moving credentials out does not automatically make it safe to share publicly. Backups may retain old plaintext credentials; this does not promise secure erasure or automatic cleanup/recovery of old identities.

`AGENTS.md` remains a separate global-instructions file, included in the agent editor and untouched by migration. The old JSON filenames above are startup migration inputs only, not alternative save locations. One-time conversion runs exclusively at Server startup, after acquiring the instance lock and before application settings load. It accepts those seven files only if no main exists, or upgrades the previous inline-credential `config.json` v1. Under the shared configuration lock, it collects actual source bytes, validates JSON and limits, prepares the conversion, and verifies exact private backups with `SHA256SUMS` under `.config-backup-<time>-<id>/`. Backups include v1 `config.json` and an existing `key.json` as applicable, not just the legacy filenames. It publishes keys before main-file references, verifies the published pair and required durability, then removes only unchanged legacy source originals. The converted v1 main is replaced by the current main, not deleted afterward. The private backup is retained, not automatically restored. See [storage contracts](./architecture.md#unified-configuration-storage).

An existing `config.json` is always the sole source, including for a v1 upgrade: leftover old files are ignored, not merged, even for a missing section. Once the current main is present, later starts only validate the current format and referenced keys; healthy starts do not scan legacy paths, import old data or create another migration backup. Malformed JSON, a missing/unsupported version, or invalid references/missing referenced key entries fail closed, never triggering reimport, fallback to old files, inline secrets or backups, or an automatic reset. Section validation keeps its existing typed behavior. Older binaries must not open the same migrated configuration directory. Account authorization directories and OAuth/login snapshots are untouched; old account identities are never restored automatically.

Normal reads and writes use only the current `config.json` v2 and `key.json` v1. There is no runtime legacy data or credential fallback, and no migration on a library’s first write. Normal access to old or unmigrated data reports “start Vista to migrate” instead of importing or copying old values. The fresh-empty-root initialization described above is the only initialization case for explicit writes; it does not convert old state.

These are runtime user files, separate from repository source and embedded defaults. Two additional files are generated, not editable configuration: `omp-models.json` holds the downloaded model catalog, and `model-catalog-status.json` holds catalog update status and scheduling. They do not count toward the three fixed user files; per-account authorizations, skill folders, SQLite/runtime `state/` and browser preferences also stay separate.

All main/key-document writers share the cross-process `state/config.lock` and update their section in the latest main document, preserving other sections and credentials rather than replacing the root with a public API projection. A credential update first stages new immutable references and key entries while retaining old entries, then publishes the main references, and only then removes previously active references dropped by that committed update. Existing unreferenced entries, including those left by interrupted writes, are not blindly garbage-collected. Each file replacement is atomic, but the two files are not a single atomic transaction. Secret-bearing reads recheck the main snapshot after reading keys and retry publication/pruning races; nonsecret section reads do not load the key file.

Typed settings APIs resolve bundles internally for runtime consumers and keep their existing save and runtime side effects. This storage change does not add global hot reload for direct file edits: agent and client-identity settings retain their existing direct-read boundaries; cached model, MCP, search and capacity settings still require their existing reload/start behavior.

## About Vista and service controls

About Vista presents these sections in order:

1. Brand, version, and introduction.
2. The model catalog.
3. Full reset, visible only in Debug mode.
4. Restart Vista, visible whether or not Debug mode is enabled.
5. Build information.

The adjustments button in the top right opens **Advanced settings** in a secondary dialog with vertical tabs on the left for client identity (User-Agent), memory and capacity, service configuration, and Debug mode. These editors load only while the dialog is open. Switching tabs retains every draft; an invalid draft locks the other tabs until corrected; **Save changes** applies all changed tabs, including Debug mode. Invalid fields open their tab before any write, and dismissing unsaved changes requires confirmation. A port change is confirmed before saving any tab and is submitted last; a failed section keeps its draft for retry, while earlier successful sections remain saved.

Service configuration edits the listening port, an integer from 1 to 65535.
When **Save changes** includes a port change, a separate **Save and restart** confirmation shows the impact on active tasks and managed background processes.
Before saving, an independent successor binds the target port on the configured IPv4 listening address and keeps that socket through startup. If reservation fails, the current instance and saved configuration remain unchanged, and the form preserves the draft and displays the error.
A revision conflict aborts the reservation instead of overwriting another edit. Unchanged listening ports can be saved without a restart.
After acceptance, the old tab stays open with the new address and an explicit **Open Vista in a new tab** link. Direct HTTP access keeps the browser's hostname and changes its port; HTTPS proxy access retains the public origin, and proxy upstream changes remain deployment work. Reset navigation follows the same browser-origin rule. Acceptance is not readiness; a bounded, credential-free readiness image check confirms that the entry serves HTTP. Lost responses and timeouts remain unconfirmed and never automatically repeat a lifecycle mutation.
Port changes retain server-side data, including saved composer drafts. Browser preferences and unacknowledged edits remain at the previous origin; Vista does not copy browser identity or login state across origins.
Ordinary startup priority remains CLI `--port` > `VISTA_PORT` > saved port > default. The separate **Restart Vista** action keeps the actual listening port rather than applying a pending saved port.

Restart Vista is a regular secondary button and always opens a confirmation dialog.
The dialog shows active-conversation and managed-background-process counts when available; unavailable counts are identified as unknown, not zero.
Its warning explains that execution is interrupted during restart, unfinished agent tasks continue from saved context afterward, and managed background processes stop without automatic restoration. Canceled tasks and questions awaiting an answer remain stopped.
Restart keeps conversations, resources, settings, browser preferences and drafts, the configuration directory and the actual listening port, without opening another browser.
A control process independent of the old Server reuses the CLI restart flow: stop → wait for the instance lock to be released → start.
It loads the current binary at the same executable path, which can activate a newer binary already placed there; it does not download or install updates or switch to another checkout.

After confirmation, the dialog shows indeterminate restart/reconnection progress.
Success requires the shared state SSE connection to be ready with an `instanceId` for a new Server process; HTTP 202 only acknowledges acceptance, and an internal App or SSE epoch change is not confirmation.
A timeout or lost response leaves the result unconfirmed rather than automatically sending another restart request.
Retry connection only reconnects to check the result; it does not send another restart POST or replay interrupted work.

With Debug mode enabled, About Vista offers a confirmed full reset. It stops running tasks, managed background processes and logins, then deletes all conversations, attached resources, connections and credentials, user skills, global instructions and other Vista settings. Embedded system skills remain available. The current browser's Vista preferences and drafts are cleared, the application runtime restarts inside the same Server process, and the page opens the first-use screen at its new address. External files and services, including files previously changed by tools, are not reverted. The listener uses the default port after reset, or the port specified by the process environment; the previous launch port is discarded. Browser preferences in other clients and settings supplied through the process environment are outside this reset.

## Activity and usage

Settings → Usage uses one 7/30/90-day period for daily activity/consumption trends and a weekday/hour activity heatmap, displayed in the viewer's timezone.
An open statistics view also updates at local hour/day boundaries without requiring new activity or usage records.
Each heatmap cell shows mean active minutes for that weekday/hour across observed local dates; inactive occurrences count as zero, while dates before collection and future hours are excluded.
An active minute contains a click, typing, or scrolling; simultaneous interactions across clients count once, while idle pages and background execution do not count.
The total uses upstream-reported input plus output tokens, counting cache and reasoning subsets only once, across conversations, child tasks, compaction, and title generation.
Successful calls without usable reported usage are identified and excluded from the total; failed requests without usable usage are not counted.
The total is shown as an approximate comparison with familiar texts; hover, tap, or focus it for the original token count and a brief explanation. See [usage statistics](./usage-statistics.md) for the reference sources and conversion rules.
Existing retained model-result records are imported once; the page identifies when complete collection began, and does not invent historical interaction activity.
Records are kept for 90 days, matching the longest available view; selecting a shorter period does not shorten retention.
Conversation deletion or withdrawal does not deduct retained consumption; a confirmed statistics reset in Usage or a full Vista reset removes the statistics.

## Current boundaries

Vista listens on all IPv4 interfaces (`0.0.0.0`) by default, accepts any request Host and browser Origin, and permits credentialed cross-origin access. Set the optional startup environment variable `VISTA_HOST` to a specific IPv4 address to restrict listening. Access restrictions belong to the deployment environment or reverse proxy; the service has no user login or per-client data isolation and does not terminate HTTPS. Tools run with the service user's permissions, without per-tool approval or filesystem rollback. Conversations share the real filesystem and have no fixed project directory; tools require explicit target paths. Optimistic checks in file-writing tools do not cover arbitrary shell writes.

Image attachments currently accept PNG, JPEG, WebP, and GIF, up to 50 MiB each. The model can import local images through `read_resource`, including downloaded files and extracted frames. Audio/video input and automatic frame extraction are not supported. There is no built-in LSP, dedicated Git workflow, or terminal UI. Model/protocol metadata and local simulations do not certify every upstream account or model; see [providers](./providers.md) and [verification](./testing.md).
