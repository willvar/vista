# Worker and background task lifecycle

[简体中文](./process-lifecycle.zh-CN.md)

On Linux and macOS, each conversation Worker leads a separate process session. Shell and local MCP processes have their own process groups and retain membership in the Worker's session. The Worker cleans up its children on normal exit; the Server cleans up and reaps a Worker after an unexpected exit. Linux checks identity using `/proc` start times and pidfds; macOS uses `sysctl` start times and session IDs. The Server persists Worker PIDs and start identities, then checks them and handles leftovers at the next startup. macOS has no Linux parent-death signal: IPC EOF triggers Worker cleanup after Server exit, and subsequent startup also checks persisted Worker identities.

Windows uses Job Objects with `KILL_ON_JOB_CLOSE`. Before launching managed children, the current process enters an outer Job that children inherit at creation. Workers, shells, and local MCP processes also start suspended and enter their own Jobs before resuming. This covers parent failure during startup and prevents rapidly spawned descendants from escaping registration. Job handles are not inherited by children; the OS terminates the Job's process tree when its owning parent exits or crashes. Explicit stops also terminate the tree. Persisted identity uses Windows process creation time to avoid killing a reused PID. The CLI detaches the Server from its console and from terminal/SSH Jobs that permit breakaway, so the service survives closure of the startup connection. Managed Workers and tools remain in Vista Jobs.

On Windows, double-clicking `vista.exe` in Explorer starts or reopens the running instance and launches the default browser. Only the Explorer launcher's console is hidden; terminal commands retain their normal output. Startup failures show a native dialog with the cause and log path. If the browser command cannot start, a dialog provides the running instance's address.

The Windows Server owns one notification-area icon and a native UI thread, started through `server.Run`'s readiness hook after the instance record is published. Reopening does not create another icon. Mouse single/double activation is coalesced into one `start` command; the context menu offers `restart`, a parsed native status window, and `stop`. Status reads `/api/status` with a deadline, uses a scrollable, selectable read-only control, and does not block the tray message loop. Closing it leaves the service running. Shutdown closes status and removes the icon; the hidden top-level tray window handles `TaskbarCreated` to restore the icon after Explorer restarts. A noninteractive Windows session without Explorer continues serving without a visible icon.

Tray lifecycle commands run as explicitly detached processes, so Restart can finish after the old Server exits. The Server's outer supervision Job permits explicit breakaway; each managed child's individual Job still forbids it and is assigned before resuming the child. Normal children still inherit the outer Job at creation. Hidden tray-action failures retain native error reporting, while ordinary terminal commands keep their existing output.

Closing a Vista conversation stops its Worker. Switching pages or closing the browser does not.

A confirmed full reset restarts the application runtime inside the Server process. `internal/server/reset.go` blocks new API work, cancels the old runtime context, drains requests and `App.background` work, stops Workers and verifies remaining ownership records before closing SQLite and deleting user data. All asynchronous operations which can write runtime files, credentials, or stored state must join `App.background` or be synchronously joined by a tracked caller. The instance lock stays held. After reopening fresh data, `runtimeListener` replaces the listening socket if the reset port changes; the old accepted reset request survives long enough to return the new address. A failure keeps other APIs unavailable while permitting reset retry and shutdown.

Background shell jobs and `detached` subtasks belong to the Vista conversation and may outlive one foreground execution or its cancellation. `required` subtasks block parent submission; `best_effort` subtasks are canceled during parent finalization. Explicitly stopping a subtask cancels its existing descendants, including detached descendants. Normal parent finalization preserves detached work.

Subtask startup is persisted and acknowledged before returning the task ID or making model requests. Terminal state and reports must also be durably acknowledged before parent collection. Background tasks and their descendants may continue writing model text, tool records, and reports to their original execution trace after the parent ends; they do not create new formal assistant messages. State lives in `agent_tasks`; reports reuse events and model-output chunks. Worker exit, conversation closure, or Vista restart records unfinished tasks as interrupted without automatically resuming side effects.

Tool execution waits for a persisted, acknowledged start event. Tools whose results cannot be confirmed are recorded as unknown. Running background subtasks do not turn a completed foreground execution into a failure. Explicitly stopping a subtask does not alter an already submitted foreground reply.

Foreground shell and large tool output are saved as artifacts; background shells are saved as jobs. Interruption retains saved bytes and explicitly records whether output is complete. Unix cleanup covers descendants still in the Worker's process session or a tool's process group; it cannot guarantee cleanup of external programs that deliberately detach with `setsid`. Windows Jobs cover normally spawned descendants, not processes created through external mechanisms such as system services.

`make test integration` covers Worker crashes, Server crashes, and combined Server/Worker crashes, and is included in `make test all`. The lower-level Linux scripts are `scripts/worker_crash_smoke.mjs` and `scripts/background_job_smoke.mjs`; the former accepts `VISTA_CRASH_MASTER=1`, the latter `VISTA_DOUBLE_CRASH=1`. Direct script runs need isolated test state and `VISTA_BIN` pointing to the executable under test.

Cross-platform tests live in `internal/platform/platform_test.go`; Windows additionally checks that abrupt parent exit closes managed Jobs while an explicitly detached control process survives. `TestNativeApplication` in `cmd/vista/platform_test.go` checks startup/shutdown, configuration, Workers, shells, cancellation, background jobs, and crash recovery using the real application executable. `TestNativeResetPort` checks reset, a changed port, instance discovery, and retry after a port conflict. `TestNativeWindowsDesktopLauncher` checks the Explorer launch path with private parent/browser executables, instance reuse, and a native startup-error dialog. `TestNativeWindowsTray` checks icon registration, click notifications, popup dismissal, parsed status, icon restoration, Restart with a live Worker, and Stop. `TestNativeWindowsTrayLongStatus` checks long Unicode status, scrolling, and shutdown with a status window open. Set `VISTA_TEST_BINARY` and run on the target platform; icon checks require an interactive Windows session with Explorer.
